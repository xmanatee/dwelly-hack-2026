# Planner — зона Веры

Публичный вызов остаётся `await planner.plan(context: str) -> Plan`.
Реализация модели и скиллов живёт в [implementation/](implementation/README.md).
Сейчас используется `HumanReviewPlanner`: константная заглушка, без модели и скиллов.

Параметры экземпляра: `ActionProfile` (production/contest), модель и знания. Профиль
не надо прятать в тексте пользователя или передавать новым аргументом каждого вызова.
`profile.catalog()` выдаёт JSON-каталог с точными схемами аргументов. После генерации
вызывать `profile.validate_plan(plan)`. Исполнитель повторяет проверку до действий.

| Action | Аргументы | Значение |
| --- | --- | --- |
| `reply_to_trigger` | `message` | Ответить в исходную email-цепочку, звонок или тикет. |
| `send_email` | `recipient, subject, message` | Новое исходящее письмо. |
| `call_customer` | `phone, message` | Новый исходящий звонок с заданным сообщением. |
| `update_ticket` | `ticket_id, status, note` | Изменить тикет, в том числе закрыть. |
| `handoff` | `queue, reason` | Передать кейс указанной команде. |
| `calculate` | `expression, rounding, basis` | Посчитать по известным числам и правилу; `basis` объясняет их источник. |

У всех действий есть уникальный `id`. План — последовательный список конкретных
действий с `decision`, `disposition` и коротким публичным `rationale`.
Получить новые сведения от человека можно явным сообщением и `awaiting_input`.
Чтение базы относится к сборщику контекста. Произвольный Python/SQL не является действием.
Нет универсальной автоматической операции «начислить долг»: формулу и исходные числа
нужно обосновать доступными фактами и правилами.

Пример: `calculate(id="total", expression="125.50 + 24.50", rounding="cents", basis="Two supplied invoice amounts")`,
затем `reply_to_trigger(message="Total: {{total.value}}")`. Это единственная подстановка:
ссылка на значение предыдущего расчёта в сообщении/заметке/теме письма. Ссылки вперёд
и неизвестные значения отклоняются до начала исполнения. Разветвлений и языка программ здесь нет.

`profiles/production.json` сейчас разрешает mock-исполнение. `profiles/contest.json`
сохраняет тот же предметный словарь, но допускает только предложения. Его нельзя
передать исполнителю. В контесте план идёт в отдельный генератор ANSWER/REASONING;
создание красивого ответа не должно менять решение или заявлять выполненные операции.
Разные наборы разрешённых действий можно задать в собственном `ActionProfile`,
не создавая вторую реализацию Planner. Реальные банковские действия добавляем только
вместе с их адаптерами и определёнными полномочиями.

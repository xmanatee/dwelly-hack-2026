# Целевая архитектура: продукт, Planner и Hackathon Solver

Уточнено по направлению команды 10 октября 2026. Первый рабочий каркас уже реализован: три канала → Markdown-контекст → Planner-заглушка → mock-исполнитель. [Запуск, файлы и интерфейсы подключения](../../examples/production/README.md). Реальные источники/действия, Planner Веры и отдельный Solver ещё предстоят; прежние результаты не являются baseline нового планировщика.

Общий Planner расположен в продукте; Solver импортирует его. Кнопки выделяют пути, клик по иконке показывает описание. По умолчанию текст скрыт.

## Два пакета, один Planner

**Продукт `dwelly_bot`** принимает обращение из любого канала, собирает контекст, выбирает решение через Planner, исполняет конкретные действия и возвращает результат. Planner — публичный компонент этого пакета.

**Отдельный пакет `hackathon_solver`** готовит контестный вход, импортирует этот Planner и преобразует его план в ответ для хакатона. В продукте нет зависимости от Solver, формата кейсов организатора или контестного оценщика.

```text
Production: канал → триггер → сбор контекста → Planner → исполнитель действий (включая ответ в канал)
Hackathon:  кейс → подготовка контекста → импортированный Planner → генератор ответа → два файла
```

Планировщик — чёрный ящик с простым внешним протоколом:

```python
class Planner(Protocol):
    async def plan(self, context: str) -> Plan: ...
```

Этот интерфейс уже доступен через `from dwelly_bot.planning import Planner, Plan`. На входе один длинный текст, обычно Markdown; на выходе структурированный `Plan`. Модель, скиллы, промпты и число внутренних проходов скрыты внутри реализации и конфигурации экземпляра. Они не усложняют протокол вызова. Продакшен, демо и Solver используют одну реализацию и одну выбранную версию конфигурации.

## Зоны ответственности

| Зона | Ответственность | Граница интеграции |
| --- | --- | --- |
| Никита | Тестовый мир: customer, bank, другие сущности, таблицы и связи | Источники для сборщика контекста и проверки исполнения; внутреннюю схему генератора он определяет отдельно. |
| Вера | Planner, его скиллы и знания, улучшение качества планов; генератор `ANSWER` / `REASONING` в Solver | Публичный протокол `text → Plan` и отдельный интерфейс генерации ответа по плану. |
| Наша часть | Архитектура продукта и пакетов, контракты, интеграция каналов, контекста, исполнения и Solver | Границы компонентов, общий конвейер и воспроизводимый путь эксперимента. |

Тестовые таблицы Никиты не становятся частью интерфейса Planner. Компонент Веры — сам Planner и подготовка контестного ответа; прежнее предположение о её роли как поставщика тестового контекста заменено этим распределением.

## Что означает Plan

План содержит **принятое решение и конкретный способ его выполнить**. Вся доступная для принятия решения информация уже находится во входном контексте. Planner не обращается к CRM, банковской базе, почте или поиску. Подбор скиллов и внутренние проходы модели допустимы внутри компонента; они не собирают новые факты о клиенте.

Мягкая схема для первого прохода:

| Поле | Смысл |
| --- | --- |
| `decision` | Что решили сделать и ради какого результата. |
| `disposition` | Например: выполнить действия, ответить сразу, передать человеку, запросить недостающие сведения или отказать. Названия пока не закреплены enum. |
| `actions` | Упорядоченные конкретные операции: тип действия, адресат/цель, необходимые параметры, ожидаемое подтверждение. Может быть пустым при немедленном ответе. |
| `response` | Предлагаемое сообщение клиенту или оператору с честным статусом запланированной работы. |
| `rationale` | Короткое публичное обоснование по фактам и применимым правилам; значимые неопределённости. |

Это не требование генерировать исполняемый Python или строить универсальный движок графов. Точные поля уточняются на кейсах. Контекстные ссылки, версия скиллов, конфигурация модели и хеши сохраняются в трассе запуска; они не требуют дополнительных аргументов публичного метода.

### Решения принимаются до исполнения

Если контекст уже подтверждает факт, от которого зависит маршрут, Planner выбирает маршрут сейчас. Он не выдаёт исполнителю «ещё раз прочитай ту же запись и реши, кому передать».

Если применимые правила требуют передачи человеку из-за признаков уязвимости, план сразу содержит эту передачу и необходимые данные для неё. Если факты указывают на возможный фрод, конкретные действия определяются предоставленными процедурами и полномочиями: здесь не вводится универсальное правило блокировать счёт или совершать другую банковскую операцию.

Немедленная передача — полноценный короткий план. «Терминальный» означает, что автоматическое принятие решений на этом этапе закончено; сама передача всё ещё должна быть выполнена и подтверждена. При отсутствии подтверждения нельзя сообщать, что она состоялась.

Запросить **действительно отсутствующую** информацию допустимо: позвонить клиенту, отправить конкретный вопрос, получить подтверждение адреса. План определяет вопрос, адресата и состояние ожидания. Последующий ответ становится новым событием с новым контекстом; исполнителю не поручается самостоятельно придумывать дальнейшую политику. Недостающие технические параметры также нельзя молча оставлять для угадывания исполнителем.

## Производственный конвейер

### Канал и триггер

Звонок, email, SMS или назначенный тикет превращаются в общий `Trigger`: идентификатор события, время, запрос/транскрипция, подсказки для поиска клиента, корреляция и маршрут ответа. Подтверждённая аутентификация передаётся явно; наличие имени или email само по себе её не доказывает.

### Сбор контекста

Сборщик разрешает идентификаторы и связи, собирает доступные записи, историю и вложения. Он сохраняет источники, время среза, неоднозначные совпадения, ошибки и неизвестные значения. В текст также входят доступные действия и ограничения полномочий, чтобы Planner не выдумывал возможности исполнителя.

На границе Planner всё это сериализуется в **один Markdown-текст**. Структурированный снимок можно сохранять рядом для аудита и воспроизведения, но Planner не обязан знать его схему. Доступность ограничена моментом события и ролью запроса. При отборе длинного контекста пропуски явно отмечаются.

Скиллы — версионированные процедуры и знания внутри компонента Planner. Внешние письма и документы во входном тексте остаются данными, а не системными инструкциями.

### Исполнение и возврат результата

Исполнитель сопоставляет уже выбранные операции с адаптерами и выполняет их. Он не должен заново рассуждать о бизнес-решении, выбирать эскалацию или дописывать план. Проверка схемы, прав, идемпотентности и технических предусловий остаётся обязанностью runtime: это не повторный сбор контекста ради выбора решения.

При неожиданном состоянии исполнитель останавливает затронутое действие и возвращает явный результат. Существенно новые сведения могут запустить отдельный цикл через сборщик и Planner. Это исключение, а не обязательная часть каждого плана.

Журнал различает предложение, попытку, подтверждённое выполнение, отказ и неизвестный исход. Повторное событие не повторяет действие; таймаут не считается успехом. `ExecutionResult` содержит подтверждения, ошибки и состояние: завершено, ожидает сведений, передано либо не выполнено.

Возврат в канал — действие плана `reply_to_trigger`, которое исполнитель направляет в исходную email-цепочку, активный звонок или комментарий тикета. Отдельного обязательного блока доставки после исполнения нет: иначе ответ мог бы отправиться дважды. Явные `send_email` и `call_customer` создают новое исходящее обращение, `update_ticket` меняет статус, `handoff` запрашивает передачу человеку. Каналы справа на схеме показывают адресатов этих действий. Закрытие тикета не происходит автоматически. Для долгой работы реальный адаптер позднее сможет поддержать промежуточный ответ и последующее событие.

## Hackathon Solver

Solver имеет собственный вход, CLI и контестные адаптеры. Его зависимости направлены к публичному API продукта:

```text
hackathon_solver → dwelly_bot.planning
        ↓                 ↓
контестные артефакты    общий Plan
```

1. **Загрузка и подготовка кейса.** Адаптер выбирает момент решения и собирает историю, доступный контекст и вложения в один текст. Ответы, разметка, будущие события и исходы удерживаются отдельно для оценки. Удаления поля с ответом недостаточно: завершённая история тоже может раскрывать решение. Исходные файлы сохраняются без изменения байтов. Семантика публичных данных описана в [контракте данных](../../dataset/README.md).
2. **Планирование.** Solver импортирует Planner и вызывает `await planner.plan(context_text)`. Здесь нет отдельной контестной версии логики решения.
3. **Генерация ответа.** Отдельный компонент Веры получает `Plan` и при необходимости тот же видимый текст контекста для точных ссылок. Он может сделать дополнительный LLM-вызов и вернуть два текста — `answer` и `reasoning`. Он не получает скрытые исходы и не меняет принятое решение. Если плана недостаточно, это ошибка/сигнал для улучшения Planner, а не разрешение незаметно перепланировать внутри генератора.
4. **Запись артефактов.** Простой writer сохраняет `ANSWERS/<case>/ANSWER.md` и `ANSWERS/<case>/REASONING.md` для соответствующего формата сдачи. Сохраняются исходный план, вход генератора и его результат. Существующие ограничения на practice-экспорты и идентификаторы организатора продолжают действовать.
5. **Оценка сохранённого результата.** Отдельно оцениваются план, верность преобразования и итоговый контестный ответ. Оценщик может иметь ретроспективные материалы; Planner и генератор их не получают.

`ANSWER.md` выражает решение, предлагаемые действия и подходящий текст ответа. `REASONING.md` объясняет основания по доступным фактам и правилам; это публичное обоснование, не скрытая цепочка мыслей. В контестном пути исполнитель не запускается, поэтому никакой этап генерации не должен объявлять запланированные банковские действия выполненными.

## Структура репозитория после миграции

Минимальное разделение — основной пакет в существующем `src/` и отдельный устанавливаемый пакет Solver в uv workspace:

```text
pyproject.toml                    # основной пакет + uv workspace
src/dwelly_bot/
    planning/                    # публичные Planner / Plan, реализация Веры
    skills/                      # знания Planner
    prompts/                     # инструкции Planner
    channels/                    # триггеры и доставка
    context/                     # сборка текста
    execution/                   # выполнение выбранных операций
    harness/                     # производственная оркестрация
packages/hackathon_solver/
    pyproject.toml               # зависимость от dwelly-bot через workspace
    src/hackathon_solver/
        adapters/                # контестные кейсы → видимый текст
        generation/              # Plan → answer / reasoning, компонент Веры
        export/                  # файлы и формат сдачи
        evaluation/              # оценка сохранённых результатов
        runner.py                # оркестрация Solver
        cli.py
experiments/                     # зафиксированные сравнения и результаты
```

Это **полная целевая структура**. Уже созданы `channels/`, `planning/`, `execution/`, `context/collector.py` и `harness/production.py`; отдельного пакета Solver пока нет. Установка продукта не должна требовать Solver или зависимостей его оценщика. Для повторного использования runner, model pool, budget и journal сохраняем общий инфраструктурный слой; не копируем их в Solver. Его публичную границу уточняем при переносе, без импорта приватных функций оценщика в Planner.

## Как оптимизируем

Главная единица улучшения Веры — **текст → Plan**: скиллы, инструкции, выбор знаний, модель и структура решения. Проверяем правильность выбранного действия, полноту параметров, достаточность оснований и отсутствие лишних проверок уже известных фактов. Короткий немедленный маршрут может быть лучшим планом; количество шагов не является целью.

Генератор ответа — отдельная переменная эксперимента. При сравнении Planner фиксируем его версию и настройки; при изменении генератора подаём одинаковые сохранённые планы. Дополнительно считаем итоговое качество всего Solver, чтобы отличать ошибки решения от искажений при формулировке ответа.

Для baseline и кандидата фиксируем одинаковые входные тексты, срезы данных, версии скиллов и формат плана. Сохраняем ошибки, расходы, задержки и парные регрессии. MiniMax baseline и Sonnet candidate на новом контракте потребуют нового запуска: исторические captures прежнего агента его не заменяют. Разделяем материал для разработки и отложенную проверку; оценка не возвращается во вход текущего кейса.

Интеграционные сценарии в мире Никиты отдельно проверяют, можно ли выполнить план и вернуть подтверждённый результат в канал. Перед сдачей проверяем, что демо и Solver импортируют один Planner и выбранную конфигурацию, а генератор сохраняет его решение.

Текущий шаг выполнен: публичный контракт и вертикальный проход «триггер → текст → заглушка плана → mock-действия». Следующие подключения — данные Никиты через `ContextSource`, реализация Веры через `Planner`, отдельный Solver с генерацией двух файлов, реальные адаптеры действий. Конкретный цикл оптимизации уточняем по мере появления Planner; универсальный оптимизатор сейчас не строим. Исторические результаты сохраняются. Готовность к продакшену требует проверенного runtime и адаптеров; сама схема этого не подтверждает.


## Что уже можно запустить

`dwelly-bot demo` обрабатывает email, звонок или тикет через один `ProductionPipeline`. Сохраняются исходный вход, маршрут ответа, точный `context.md`, план и результаты с журналом этапов. Обязательные идентификаторы, типы действий и временные границы проверяются Pydantic и адаптерами.

`HumanReviewPlanner` не вызывает модель и не читает скиллы: всегда выдаёт передачу в `human-support` и ответ в исходный канал. `MockExecutor` помечает все эффекты как симуляцию, останавливает последовательность при ошибке и защищает от повторов в пределах одного экземпляра. Это работающий каркас интеграции, а не заявленная готовность реального банка.

`ContextSource.lookup(query)` — место подключения баз, истории и документов. `HintExtractor.extract(text, supplied)` — место возможного лёгкого LLM-парсинга; сейчас реализованы только буквальные email/референсы и переданные каналом подсказки. Mock-источник использует готовую принадлежность записей кейсу. Поиск связей между таблицами и разрешение неоднозначных имён остаются за реализацией источника.
